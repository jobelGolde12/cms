# Admin Officer — Employee Records Management

> STATUS: **IMPLEMENTED** (October 2026). Adds the `admin_officer` role's
> operating domain: employee records, 201 files and service credits —
> strictly isolated from all student data.

## 1. Role summary

| Item | Value |
|---|---|
| Role key | `admin_officer` |
| Role label | Admin Officer |
| DB role id | `role-admin-officer` |
| Domain | Employee records ONLY |

The Admin Officer is an internal school personnel-records administrator. They
manage employee profiles, 201 files and service credits. They hold **zero**
student-facing permissions.

### Permissions (seeded via `src/lib/permissions.ts` → `scripts/seed.mts`)

- `dashboard.view`
- `employees.view` / `employees.create` / `employees.update` / `employees.archive`
- `employee_201.view` / `employee_201.manage`
- `service_credits.view` / `service_credits.manage`
- `reports.view` / `reports.generate`
- `audit_logs.view`

**Explicitly withheld:** every `students.*`, `guardians.*`, `enrollment.*`,
`grades.*`, `attendance.*`, `behavior.*`, `assessments.*`, `health.*`,
`interventions.*`, `verification.*`, `duplicates.*`, `qr.*`,
`documents.*`, `users.*`, `settings.*`.

Also see `documentation/security/role-permission-matrix.md`.

## 2. Student isolation (security boundary)

Enforced server-side, not in the UI:

1. **Permissions** — `src/lib/permissions.ts`: `ADMIN_OFFICER` grants no
   student permission key; `hasPermission()` gates every page route and every
   server action via `requirePermission()` / `getAuthorizedUser()`.
2. **Row scope** — `src/lib/scope.ts#studentScope()`: `admin_officer`
   resolves to a never-true SQL predicate (`1 = 0`), so even a hypothetical
   direct query for students returns no rows.
3. **Routes** — `/students*` and every student page/actions redirect or deny
   (`employees` module pages deny anyone without `employees.view`, etc.).
4. **Header search** — the global student search in the app shell renders
   only for roles holding `students.view`.
5. **Dashboard** — `/dashboard` branches on `user.role === "admin_officer"`
   and renders `OfficerDashboard` (`src/components/dashboard/officer.tsx`),
   which queries only employee tables. No student dashboard queries run on
   that render path at all.
6. **Tests** — `src/lib/__tests__/rbac-roles.test.ts` asserts the admin
   officer holds no student-facing permission, and
   `src/lib/__tests__/employees.test.ts` covers the employee domain rules.

Manual QA performed against role isolation: every student route attempt as an
Admin Officer lands on `/dashboard?denied=…` (route guard) or is rejected by
the action guard (action returns a permission error).

## 3. Database changes (migration `drizzle/0004_*.sql`)

Three new tables, following existing conventions (text ids, `unixepoch()`
timestamps, `created_by`/`updated_by` audit fields, index + unique
constraints):

### `employees`
- `employee_number` unique (`EMP-YYYY-######`, generated by
  `src/lib/employee-number.ts` when not supplied).
- Personal: first/middle/last/suffix name, birth date, sex, civil status,
  address, contact number, email, emergency contact (name/relation/number).
- Employment: position, designation, appointment status, employment type
  (teaching/non-teaching/support), department, date hired, date of
  appointment, salary grade, step.
- Government/personnel: GSIS, PhilHealth, Pag-IBIG, TIN, PRC license,
  eligibility.
- Lifecycle `status`: `active` | `inactive` | `archived` (archive is a soft
  delete; history preserved).

### `employee_201_records`
- One row per personnel document. `category` ∈
  personal_information, appointment, eligibility, training, performance,
  leave, government, certificate, memorandum, other.
- `title`, `description`, `record_date`, `file_reference` (set null — no
  file-upload dependency introduced in this change).
- `is_archived` soft-archives entries; records are never physically deleted.
- Cascades on employee delete.

### `service_credit_transactions`
- Auditable ledger: `type` ∈ `earned` | `consumed`, positive decimal
  `credits` (unit: days), `transaction_date`, `reason`, `reference_document`,
  `remarks`, `created_by`/`updated_by`, timestamps.
- **No stored balance column.** The balance is always derived from the
  ledger (`computeBalance()` in `src/lib/employees.ts`), which keeps history
  auditable and prevents manual balance edits.

## 4. Service credit rules

```
Current Balance = Σ(type = earned) − Σ(type = consumed)
```

- Consumed transactions are validated **against the live ledger** — an insert
  or correction that would drive the balance below `0` is rejected with the
  available balance shown (`validateCreditAmount()`).
- Corrections (`updateServiceCreditTransaction`) are edits in place plus an
  audit row; the previous values are preserved in `audit_logs.old_values_json`
  rather than a destructive rewrite.
- Page `/employees/[id]/service-credits` shows Total Earned, Total Consumed,
  Available Balance and the filterable transaction history.
- Page `/service-credits` is the all-employee overview with per-employee
  earned/consumed/balance badges and school-wide totals.

Example verification (also unit-tested): earn 10, consume 3 → balance 7; earn
5 more, consume 2 more → earned 15, consumed 5, balance 10.

## 6. Validation

`src/lib/schemas.ts`:

- `employeeFormSchema` — required names/sex; realistic working-age birth date
  (18–75, real calendar dates, no future dates); PH phone formats
  (`isValidPHPhone`); email format; max lengths everywhere.
- `employee201Schema` — enum category, required title/date.
- `serviceCreditSchema` — `earned|consumed`, credits in (0, 365], required
  reason, ISO date.

Server actions (`src/actions/employees.ts`) additionally enforce:

- Employee number uniqueness with a friendly duplicate error and one
  auto-retry on a generated-number collision.
- Archived employees reject 201/credit mutations until restored.
- Every mutation logs to `audit_logs` (`CREATE_EMPLOYEE`,
  `UPDATE_EMPLOYEE`, `ARCHIVE_EMPLOYEE`, `RESTORE_EMPLOYEE`,
  `CREATE_201_RECORD`, `UPDATE_201_RECORD`, `ARCHIVE_201_RECORD`,
  `SERVICE_CREDIT_ADD`, `SERVICE_CREDIT_UPDATE`).

## 7. Seeded data / default account (development)

`scripts/seed.mts` now provisions an Admin Officer default account from env
vars (same pattern as all default roles):

```
DEFAULT_ADMIN_OFFICER_EMAIL
DEFAULT_ADMIN_OFFICER_PASSWORD_HASH   # bcrypt hash, never plaintext
DEFAULT_ADMIN_OFFICER_FIRST_NAME
DEFAULT_ADMIN_OFFICER_LAST_NAME
```

If unset it falls back to `admin_officer@local.dev` with the shared
development fallback password hash (`password123`), identical to the other
default dev accounts. **Passwords are stored hashed (bcrypt cost 10); login
uses the plaintext password.** Do not commit real hashes.

The seed also creates 10 fictional employees with 201-file entries and
service-credit ledgers. All demo data is fictional.

- Personnel-document **file uploads** are intentionally not introduced; the
  201 entry stores a `file_reference` so upload storage can be added later

  `/users`).
